# 시각 자료 카탈로그

차트·도식·배경을 **처음부터 그리지 않는다.** 이미 있는 서식과 도구를 먼저 훑고,
사용자가 고른 뒤에 만든다.

## 절대 원칙 세 가지

**1) 후보를 내밀기 전에 만들지 않는다**
사용자가 "차트 만들어줘"라고 하면 바로 코드를 쓰지 말고, 먼저 **후보 3개를 제시**한다.
취향은 내가 정할 것이 아니다.

**2) 남의 코드를 그대로 붙일 수 있는지 먼저 따진다**
카탈로그의 컴포넌트는 대부분 **React**다. 지금 쓰는 파이프라인이 파이썬이나 캔버스면
**코드는 못 쓰고 디자인 규격만 옮길 수 있다.** 이걸 먼저 말하고 시작한다.

**3) "기법을 적용하면 좋아진다"를 재보지 않고 말하지 않는다**
실제로 재라. 2026-08-30 에 `tabular-nums` 를 "흔들림이 잡힌다"고 했다가
실측해 보니 42.3px 중 0px 만 잡혔다. 원인이 자릿수 증가였기 때문이다.
→ `references/transfer-notes.md` 참고.

## 절차

### 0단계 — 무엇을 만드는지와 어디에 들어가는지 확정한다

| 물을 것 | 왜 |
|---|---|
| 무엇을 보여주나 | 시계열·비교·구성비·분포·관계 — 종류가 차트를 정한다 |
| **어디에 들어가나** | 인스타 캐러셀(1080×1350) · 릴스(1080×1920) · 문서 · 웹 · 발표자료 |
| 정지인가 움직이나 | 움직이면 감속 곡선·카운트업을 같이 봐야 한다 |
| 지금 파이프라인이 무엇인가 | **React 인지 아닌지가 갈림길이다** |

### 1단계 — 이미 있는 도구부터 훑는다

`references/catalog-tools.md` 를 읽는다. **밖에서 찾기 전에 안을 먼저 본다.**

특히 이 셋은 코드를 안 써도 바로 결과가 나온다.
- **napkin** MCP — 문장을 넣으면 도식이 나온다
- **mcp__visualize__show_widget** — 대화 안에서 바로 보이는 차트·위젯
- **mermaid** MCP — 순서도·관계도

### 1.5단계 — 그 프로젝트에 **이미 있는 서식**을 먼저 본다

**밖에서 가져오는 것은 마지막이다.** 프로젝트가 자체 타입을 갖고 있으면 거기서 먼저 고른다.

| 프로젝트 | 참고 파일 |
|---|---|
| **차트 노트 (투자 3분 노트)** | `references/chartnotes-types.md` — **카드 타입 12종.** 절차서가 *"12종이 24회차를 사실상 전부 덮는다"* 고 못 박아 두었다 |

새 타입을 만들자고 하기 전에 **주제 → 타입 대응표**를 먼저 본다.
거기 있으면 밖을 볼 필요가 없다.

### 2단계 — 외부 카탈로그에서 후보를 고른다

**1.5단계에서 못 찾았을 때만 온다.**

`references/catalog-sites.md` 를 읽는다. 사이트마다 **무엇이 있나 / 무료인가 / 어떻게 가져오나**가 적혀 있다.

### 3단계 — 후보 3개를 사용자에게 제시한다

이 형식으로 낸다.

```
후보 ① <이름>   <어느 카탈로그>   <왜 이 주제에 맞나>
후보 ② ...
후보 ③ ...

지금 파이프라인은 <파이썬/캔버스/React> 이므로
  · 코드를 그대로 쓸 수 있다   → ①③
  · 규격만 옮겨야 한다        → ②
```

미리보기를 보여줄 수 있으면 보여준다(로컬 서버·스크린샷·`show_widget`).

### 4단계 — 고른 것을 옮긴다

`references/transfer-notes.md` 의 실패 사례를 먼저 읽는다.
**옮긴 뒤에는 반드시 적용 전/후를 실측해 숫자로 낸다.**

### 5단계 — 카탈로그를 갱신한다

새 사이트를 알게 되면 `references/catalog-sites.md` 에 한 줄 추가한다.
**스킬을 새로 만들지 않는다.** 이 스킬 하나에 계속 쌓는다.

## 하지 말 것

- 사이트마다 스킬을 따로 만드는 것 — 카탈로그 파일에 줄을 더한다
- 확인 안 한 사이트를 목록에 그냥 올리는 것 — **직접 열어 보고**, 못 열면 "확인 실패"라고 적는다
- 카탈로그에 있다는 이유로 라이선스를 안 보는 것 — MIT 인지 상용인지 매번 확인한다
- 개선 효과를 재지 않고 말하는 것
